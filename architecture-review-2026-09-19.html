🎯 首要推荐：重构 web_app.py（Critical）

web_app.py — 2163行，承载50+路由，所有功能堆在一个文件里。按照 Matt Pocock 的"深度模块"标准：

  • 接口 = 50+路由处理器 + 10+全局装饰器 + 5个蓝图注册
  • 实现 = 全部逻辑都在一个文件里
  • 深度 ≈ 0（接口几乎等于实现）

每增加一个API路由，开发者需要理解整个文件的依赖关系才能安全改动。这是典型的 Shallow Module 反模式。

Before（浅层单文件）
web_app.py（2163行）
├── 50个路由
├── 5个蓝图注册
├── rate_limit/secure/pdf/exporter...
└── 所有逻辑混杂
After（深层模块化）
web_app.py（注册蓝图）
├── routes/cases.py（~200行）
├── routes/search.py（~150行）
├── routes/stats.py（~150行）
├── routes/defense.py（~200行）
├── routes/export.py（~100行）
└── shared/（中间件/工具）
💡 Locality 收益：改一个API路由只需看一个100行的文件，不用再读2163行。 💡 Leverage 收益：各路由共享的中间件统一在 shared/ 管理，测试只需mock一次。

🟡 候选3：导入路径不一致（High）

两种导入风格混用，开发者体验碎片化：

✅ 风格A（web_app.py）
from src.rate_limit import ...
from src.admin import ...
from case_loader import CaseLoader
❌ 风格B（audit.py/auth.py）
from database import db
from auth import create_auth_blueprint
# 无 src. 前缀

两种都能跑，但风格B依赖 sys.path.insert(0, 'src') hack，易在非根目录运行时报错。建议统一用风格A的 from src.xxx 显式导入。
